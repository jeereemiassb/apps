Merge Duplicate Requests for Jira Service Management

Merge a duplicate request into the one that stays open, with its comments, attachments and people.

Overview

When several customers report the same problem, agents end up answering the same thing in several requests. Merge Duplicate Requests moves everything from a duplicate into the request that stays open, links the two and closes the duplicate.

  • Merge from the request itself: ••• → Merge into another request.
  • A preview shows what will be copied and how the duplicate will be closed before anything changes.
  • The description and comments keep their original author and date. Internal notes stay internal.
  • Attachments, labels, watchers, the requester and the request participants move over.
  • Everything runs with the agent's own Jira permissions.

Getting started

  1. A Jira administrator installs the app from its Atlassian Marketplace listing.
  2. Optional: a space administrator opens Space settings → Apps → Merge requests (called project settings on some sites) to choose how merged requests are closed and whether the requester is told. Without settings, the app picks the closing status and resolution automatically.
  3. Open the duplicate request in the agent view, select ••• and then Merge into another request.
  4. Type the key of the request that stays open (for example HELP-12) or words from its summary, select Search and choose it. Select Search all projects to look outside the current space.
  5. Select Preview merge, check the options and select Merge. Keep the dialog open until it finishes.

What the merge does

StepWhat happens
DescriptionAdded to the request that stays open as a comment, with the summary, the requester and the date.
CommentsCopied in order. A header says who wrote each one and when; in internal copies it also links to the original request.
AttachmentsCopied one by one, up to 10 MB each. Larger files are listed in the merge note instead.
PeopleThe requester and the request participants of the duplicate become request participants. Its watchers become watchers.
LabelsLabels of the duplicate that the other request does not have are added.
LinkThe duplicate is linked with the "Duplicate" link type: it duplicates the request that stays open.
NotesThe request that stays open gets an internal note listing what was copied. The duplicate gets an internal note, or a public comment for its requester if you choose that.
CloseThe duplicate is moved to the closing status, with the resolution if the transition asks for one.

Comment visibility

  • Internal notes are always copied as internal notes.
  • Comments restricted to a role or group keep the same restriction.
  • Public replies stay public only if you turn on Keep public replies visible to the customer. It is on by default when both requests have the same requester, and off when they have different requesters, so one customer does not see another customer's conversation. When it is off, public replies are copied as internal notes.
  • Mentions in copied comments become plain text, so nobody is notified twice. Images and files shown inside a comment become a line like "[Attachment: screenshot.png]"; the files themselves are copied as attachments.

Running the merge again

If the dialog is closed or a step fails halfway, merge again into the same request. Comments that were already copied are recognised and skipped, and attachments with the same name and size are not uploaded twice. If something could not be copied, the duplicate is left open so you can check it.

Settings

Space settings → Apps → Merge requests. Space administrators only. The settings apply to requests merged from that space.

SettingWhat it does
Move it toThe status the duplicate is moved to. Automatic uses the first workflow transition to a "Done" status, preferring one about duplicates or resolving. If no transition leads to the chosen status, the duplicate stays open and the agent is told.
ResolutionThe resolution set when the transition screen has the Resolution field. Automatic uses "Duplicate" if the transition allows it, then "Done", "Resolved" or "Fixed", and otherwise the first one when a resolution is required.
Tell the requester by defaultWhether the option to tell the requester with a public comment starts on in the merge dialog. Agents can change it for each merge.
Public comment added to the merged requestThe text of that comment. {target} is replaced by the key of the request that stays open, and a link to it in the customer portal is added below.

Limitations

  • One duplicate at a time: open each duplicate and merge it.
  • A Jira Service Management request can only be merged into another Jira Service Management request, so its internal notes stay internal. Issues from other projects can be merged into a service request; their comments are copied as internal notes.
  • Attachments larger than 10 MB are not copied; the merge note lists them.
  • Copied comments and attachments are added by the agent who merges, with the original author and date in the header. Comment dates in Jira show when the copy was made.
  • Each copied comment is a new comment, so Jira sends its usual notifications for it.
  • Copied attachments are added to the request's attachments. They are not posted in a public comment, so customers may not see them in the portal.
  • Custom fields, work logs, votes, the request type and SLA timers are not copied.
  • Watchers other than yourself can only be added with the "Manage watchers" permission.
  • Up to 1,000 comments of the request that stays open are checked to avoid copying a comment twice.

Permissions

ScopeWhy
storage:appSave the space settings.
read:jira-workRead both requests, their comments, attachments, watchers, links and transitions, search for the request that stays open, check your permissions, and list statuses and resolutions on the settings page.
write:jira-workCopy comments and attachments, add watchers and labels, link the requests, add the merge notes and close the duplicate.
read:servicedesk-requestRead the request participants and the customer portal link.
write:servicedesk-requestAdd the requester and the participants of the duplicate to the request that stays open.

Everything runs as the agent who merges, so Jira applies that person's permissions. Before merging, the app also checks that the agent can browse, edit and comment on both requests. No egress: the app does not connect to any server outside Atlassian.

Data and privacy

The app stores only the space settings: the closing status and resolution, whether to tell the requester, and the message. It does not store account IDs or request content. While an agent merges, the app reads both requests and creates the copies in Jira with that agent's permissions; attachments are downloaded and uploaded again within the same step. Each copied comment carries a hidden comment property with the IDs of the original request and comment, so a repeated merge does not copy it twice. Nothing is logged except error names, and no data leaves Atlassian. See the privacy policy.

Troubleshooting

"Merge into another request" does not appear

The action is in the ••• menu of the new issue view. Check that the app is installed and licensed.

The dialog says I need permission on both requests

You need to be able to browse, edit and comment on both requests. The message says which permission is missing and on which request.

The duplicate was not closed

The app closes it only if a workflow transition leads to the chosen status, you can transition it, and everything was copied. Check the message at the end of the merge, the workflow of the request type and the space settings.

Some watchers were not added

Adding other people as watchers needs the "Manage watchers" permission in the space of the request that stays open.

Some participants were not added

Jira Service Management only accepts people who can raise requests in that space. The merge message says how many could not be added.

An attachment was not copied

Files over 10 MB are listed in the merge note. For others, check that you can add attachments in that space and that attachments are enabled on the site.

The app says it needs an active license

The app is paid and checks the license on every request. Ask your site administrator to check the app's subscription in Jira administration (Apps → Manage apps). During a free trial the app works normally.
